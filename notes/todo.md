## P0：影响功能正确性

### 1. 检索质量判断（不设绝对阈值）

**问题**
现在给检索设了一个绝对阈值 `min_score=0.53`，
但阈值是从 21 条测试集里"凑"出来的，过拟合小数据，数据一变就废。

**原因**
"检索结果够不够回答"是语义判断，用绝对分数切分不靠谱。
相关题和不相关题的分数边界随数据变化（当前边界仅差 0.0262）。

**改进方向**
把分数放进 Prompt，让 LLM 判断：
1. `build_rag_messages` 把每条错题的分数拼进 Prompt。
2. `SYSTEM_PROMPT` 加规则："只使用相似度 > 0.6 的错题；都不相关时回复'没有找到相关错题'。"

**和多 Agent 的关系**
- 不等价：Router Agent 判断"用户意图"，本改进判断"检索结果质量"，两者不同层次。
- 可结合：RAG Agent 内部做这个判断，Router 在顶层做路由。

**面试怎么讲**
> 我一开始用绝对阈值过滤低分结果，发现它在 21 条测试集上过拟合。
> 后来改用 LLM 判断：把分数也放进 Prompt，让模型综合文本和分数判断相关性。

### 2. 错题去重与答题记录

**问题**
同一道题重复录入时，每次都会新建一条记录，导致：
- `wrong_count` 始终是 1。
- 错题库里出现重复题目（当前二叉树有 3 条重复）。
- 无法知道用户每次选的答案。

**原因**
当初设计时没有定义"同一道题"的判定规则，`create` 逻辑只是无脑新建。

**改进方向**
采用"汇总表 + 明细表"设计：
1. **定义"同一道题"**：按 `question_content` 精确匹配。
2. **`wrong_question` 表**：只做汇总（`wrong_count`、`last_wrong_time`、`mastery_status`）。
3. **新增 `answer_record` 表**：记录每次答题（时间、用户答案、是否答对）。
4. **录入逻辑**：
   - 已存在相同题 → `wrong_count++`，`answer_record` 加一条。
   - 不存在 → 新建题 + 加一条答题记录。
5. **配套功能**：基于 `answer_record` 做"掌握度分析""答题历史查询"。

**面试怎么讲**
> 同一道题重复错，我们用"汇总表 + 明细表"设计：
> `wrong_question` 存汇总状态，`answer_record` 存每次答题明细。
> 这样既知道"错了 5 次"，也知道"每次错的时间、选的什么答案"。

## P1：影响可维护性

### 3. 没有日志系统

**问题**
排查问题全靠 `print` 和看终端输出，服务重启后日志丢失。

**改进方向**
1. 用 Python 标准库 `logging`。
2. 分级别：DEBUG / INFO / WARNING / ERROR。
3. 输出到文件 + 控制台。
4. 关键位置加日志：API 请求、LLM 调用、工具执行、Redis 操作。

---

### 4. 没有错误处理

**问题**
LLM 超时、Redis 挂了、Embedding 失败、MySQL 查询失败，
用户只看到 500，没有友好提示，也没有重试。

**改进方向**
1. **关键调用加 try/except**：LLM、Embedding、Redis。
2. **分类处理**：
   - 可重试的（网络超时）→ 重试 1~3 次。
   - 不可重试的（参数错误）→ 返回友好错误。
3. **降级策略**：LLM 挂了能不能返回"系统繁忙，请稍后"。
4. **FastAPI 全局异常处理器**：统一处理未捕获异常。

---

### 5. 新增错题后索引不更新

**问题**
现在只有启动时才判断"索引是否为空"。
已存在索引时不会重建，新增错题后检索不到。

**现状**
手动方案：删 `data/faiss_lc/` 重启，或跑 `rebuild_index.py`。

**改进方向**
1. **启动时对比条数**：索引条数 vs MySQL 条数，不一致就重建。
2. **或新增错题时增量更新**：`POST /wrong-questions` 成功后加入索引。
3. **或加一个 `/admin/rebuild-index` 接口**：手动触发重建。

## P2：影响功能完整性

### 6. 检索薄弱场景

**问题**

- **缩写问题**："BST中序遍历" 分数 0.5641（题库里是"二叉搜索树"）。
- **模糊问法**："我数据结构有哪些错题" 分数 0.5424（没有具体主题词）。

**原因**
- 缩写：Embedding 模型对缩写识别不够好。
- 模糊问法：没有主题词，和每道题的相似度都不高。

**改进方向**
- 缩写：加 query 改写（"BST" → "二叉搜索树"）。
- 模糊问法：识别意图后，按类别返回（如"数据结构" → 返回所有数据结构题）。

**面试怎么讲**
> 检索的准确率高度依赖问题的具体程度。
> 具体问题（含主题词）准确率高；模糊问题需要特殊处理。
> 这种"能力边界"分析，比单纯的准确率数字更重要。

---

### 7. 多轮对话 messages 无限增长

**问题**
LangGraph Agent 的 `messages` 每轮都追加。
多轮后可能超出模型上下文窗口，且浪费 token。

**改进方向**
1. **截断**：只保留最近 N 条消息。
2. **摘要**：把早期消息压缩成一段摘要。
3. **滑动窗口**：保留首尾，中间丢弃。
